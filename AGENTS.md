- All office-side trip cancels go through `cancelTrip()` in src/lib/cancel-trip.ts — why: one place enforces the report-documentation rule, claim voiding, notifications and audit, so cancel behavior cannot drift.
- RSNAT pre-submit cap and historical backstop share the exact-count, active-company-scoped `rsnat-trip-count` helper — why: preserve the linked-trip/2 approximation and avoid row-limit truncation or tenant leakage.
- NEMSIS CTA submissions go only through the creator-only nemsis-cta-submit function to one hardcoded CTA address; it sends either the regression fixtures or XML generated from `nemsis_cert_records`, and the generated path refuses any company that is not test/sandbox AND `nemsis_certification` (enforced in `src/lib/nemsis/cert-records.ts` and DB triggers) — why: real tenant PHI can never reach the sandbox; only the certification company's synthetic data can.
- Trip classification is two independent axes: transport kind (`src/lib/transport-vocabulary.ts`) and payer class; normalize every legacy spelling through those modules — why: four overlapping type vocabularies caused silent dialysis/$0-rate fallbacks.
- transport_kind/payer_class are filled by BEFORE INSERT/UPDATE triggers (normalize_transport_kind/normalize_payer_class mirror the TS modules) — why: one dual-write point covers every writer incl. imports and server functions; keep the SQL and TS mappings in sync.
- Billing pricing picks the charge-master row via payer_class (selectRateForPayerClass / claim trigger) and never falls back to the default rate when a class has no row — it sets claim_records.rate_flag instead — why: silent default pricing caused commercial underbilling.
- Intake visibility and validation share an intake-only axis policy; selectors persist legacy fields, never the new axes — why: hidden fields must not block intake and existing dual-write remains authoritative until cutover.

- NEMSIS conformance is checked offline with `npm run nemsis:validate <xml>`; DEM output comes from `buildDemDataSet(DemographicProfile)` and full EMS output from `buildEmsDataSet` with the optional structured `PcrExportInput.nemsis` (src/lib/nemsis/ems-record.ts; legacy trip mapping when absent), eCustom only when `custom_configuration_registered`; compliance files come from tests/nemsis/fixtures via `nemsis:gen` and are checked with `nemsis:diff` against the official references (tests/nemsis also holds the 3.5.1.251001CP2 XSDs and Schematron) — why: one repeatable validator against the official NEMSIS files, independent of the app and exporter.
- NEMSIS EMS/DEM compliance files are emitted losslessly: fixtures pass corrected live-case XML (tests/nemsis/reference/live, copied verbatim from the corrected src/lib/nemsis/fixtures/*-submission.xml sources by apply-live-corrections.mjs and apply-dem-live-corrections.mjs) as raw_reference; buildEmsDataSet stamps only eRecord.02–.04 and buildDemDataSet only dRecord.01–.03 — why: partial structured models drop repeated values and custom elements; ordinary callers retain existing rendering.
- CTA constants are generated from corrected submission XML with scripts/sync-nemsis-to-edge.sh --fixtures-only; correction scripts copy rather than insert, and fixture-only sync leaves live exporters untouched — why: submission and compliance data cannot drift or double-apply corrections.
- Production removes tenants by archive only (manage-company `delete`/`archive` → deleted_at); physical removal is test/sandbox-only via `public.purge_test_company`, whose table list must cover every RESTRICT FK to companies (guarded by src/lib/purge-test-company.test.ts) — why: retention rules and a partial non-transactional purge previously orphaned data.
- The Agency NEMSIS Profile (DEM) is stored as a tree in `nemsis_dem_nodes` (one root per section, one row per group instance, leaf values in jsonb) for the certification company only; field order/labels/Defined Lists come from `scripts/nemsis/gen-dem-schema.py` (generated `dem-schema.generated.ts`, rerun after XSD/reference changes) and `dem-tree.ts` renders it (`buildDemDataSet` with `dem_nodes`), exporting dPersonnel.901 via dCustomResults plus its dCustomConfiguration declaration — why: one schema-driven model covers every DEM section without hand-maintained per-field code, and entered data round-trips to the DEM-1 reference.
- In-app NEMSIS validation runs in nemsis-validate, which fans each unit (XSD via vendored libxml2 WASM, plus every configured Schematron file/part via SaxonJS SEF) out to nemsis-validate-unit as HMAC-signed sub-requests; the assets come from `scripts/nemsis/build-validation-assets.mjs` (add state files to SCHEMATRON_SETS, then rerun it); the gate is `decideFinalization` in src/lib/nemsis/validation.ts and only enforced rule sets gate it (`SCHEMATRON_POLICY`: national/compliance enforced, state files informational or `auto` = enforce when the file version matches the exported dataset version) — why: one unit per request fits the edge CPU budget, a failed enforced unit counts as an ERROR so nothing passes silently, and a mismatched-version state file must still run and display without blocking.
- DEM/EMS editor Defined Lists are the full XSD enumerations (attribute unions merged); `scripts/nemsis/gen-defined-list-manifest.py` verifies completeness and writes `src/lib/nemsis/defined-lists.manifest.json` (rerun after regenerating either schema module) — why: certification requires every defined-list value in the interface, provably from 3.5.1.
- Truck suggestions are pure, reuse shared feasibility/safety and the minimum-gap constant; the Scheduling board surfaces them read-only via `truck-suggestion-candidates.ts` (crewed trucks only, no rated capacity) and `useTruckDayLegs`, never through an assign path — why: advisory ranking must not mutate schedules or invent capacities or geographic distances.
- Certification EMS cases are stored as a tree in `nemsis_ems_nodes` (per case_key EMS1–EMS5, certification company only, same model as `nemsis_dem_nodes`); fields/Defined Lists come from `scripts/nemsis/gen-ems-schema.py` (`ems-schema.generated.ts`, rerun after XSD/fixture changes) and `ems-tree.ts` renders them (`buildEmsDataSet` with `ems_nodes`), exporting eCrew.901/eMedications.905 via eCustomResults with eCustomConfiguration declarations — why: the five cases are entered and resubmitted as data, not static files, and round-trip to their references.
- Office "Create PCR" (owner/manager, /trips → /pcr-office?mode=manual) creates a one-off unscheduled leg + crew (safe_assign_crew) + trip via the shared `buildTripInsert` in src/lib/pcr-trip-insert.ts, also used by the crew run picker — why: office and crew PCRs must produce identical rows and share one submit/claim/QA path.
- Census geocoding is for FACILITY addresses only: `geocode-facilities` takes facility IDs and reads only `facilities.address`, caching in company-scoped `geocode_cache` keyed by HMAC (no raw address); the client exposes only facility lookups (`src/lib/facility-geocode.ts`), never a generic address geocoder; patient or residential addresses must never be sent to Census or any non-BAA third party and require a BAA-covered or self-hosted geocoder — why: HIPAA, Census has no BAA.
